Firebase security rules checker

Paste your Cloud Firestore, Cloud Storage or Realtime Database rules to find the mistakes that leave user data open: if true, test-mode dates, rules that only check someone is signed in, files not tied to their owner and more. Free, and it runs entirely in your browser.

How to get your rules ↓
Runs entirely in your browser. Nothing you paste is uploaded, stored or sent anywhere: the check happens on this page. Paste rules only, never service account keys or passwords.

Check your rules

    How to get your rules

    The checker reads which product you pasted automatically: Firestore and Storage rules use the same rules language, and Realtime Database rules are JSON.

    1. In the Firebase console, open Firestore Database, Storage or Realtime Database and click the Rules tab.
    2. Select everything in the editor and copy it. Copying doesn’t change or publish anything.
    3. Paste it into the checker. Check each product you use: Firestore and Storage rules can go in together; Realtime Database rules go on their own.

    If your project has firestore.rules, storage.rules or database.rules.json files, those are what firebase deploy publishes. Paste those, and make sure they match what the console shows.

    What it checks

    • Rules open to everyone: allow read, write: if true;, an allow with no condition, and ".read": true in Realtime Database.
    • Test-mode rules such as request.time < timestamp.date(…) or now < …, which leave data open until a date passes.
    • Rules that only check someone is signed in (request.auth != null), which give every user everyone’s data.
    • Catch-all {document=**} rules, which override stricter rules elsewhere because Firestore combines rules with OR.
    • Storage rules that don’t tie files to a user, and uploads with no size limit.
    • Ownership mistakes: updates that let an owner reassign a document, and write rules that check resource.data so new documents are rejected.
    • Users who can edit their own role on profile documents with no limit on which fields change.
    • Email checks without email_verified, so anyone can claim an address they don’t own.
    • Realtime Database cascading: access granted high in the tree that stricter rules below can’t take away, writes that never check auth, and missing .validate rules.
    • Your own functions: calls like isSignedIn() are filled in before checking, so a helper can’t hide an open rule.

    What it can’t tell you

    The checker reads your rules for common mistakes. It doesn’t connect to your project, see your data, or know what your app is supposed to allow, so a clean result is a good start, not a security sign-off.

    Checker vs. the Rules Playground

    Firebase’s Rules Playground, in the console’s Rules tab, simulates one request at a time against your rules and tells you whether it would be allowed. It’s the right way to confirm a fix, but it only answers the questions you think to ask. This checker looks at all your rules at once for the patterns that usually leave data open, so you know which requests to try in the Playground.

    After fixing anything here, simulate reading another user’s document as a logged-out visitor and as a second signed-in user: both should be denied. The Firebase rules guide walks through those tests and how to add emulator unit tests.
