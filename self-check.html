The 10-minute AI app security self-check

Ten trust-boundary checks the products I test get wrong most often. None of them need a security background. Each is something you can run yourself with two test accounts and access to your own logs, before you ever pay anyone.

How to use this

Run them yourself. Both outcomes are useful.

None of this is a claim about any particular app. It is the set of boundaries AI and SaaS products most often miss. Each check is a few minutes with two test accounts and your own logs. If a check turns up something you can’t explain, it is worth a closer look; if it comes back clean, that is one more risk you have ruled out.

Check 01

Can one account load another account’s records?

Run it

Create a record (a note, upload, or conversation) in test account A, grab its ID or URL, then from account B try to open it by that ID.

Why

Ownership has to be enforced on the server, not hidden in the UI. Access that leaks by changing an identifier is the single most common data-exposure bug.

Check 02

Does user content end up in your logs or analytics?

Run it

Put a unique nonsense string in a test input, use the feature (including the AI call and any backup), then search your logs, crash reports, and analytics for that string.

Why

Sensitive text often gets copied somewhere you did not intend. If it turns up in plaintext where it should not, that is worth a look; if it does not, that risk is cleared.

Check 03

What are you actually sending to the model?

Run it

Capture one real request to your AI provider and read the payload. Is it only the current user’s relevant content, or more?

Why

Over-sending other users’ data, full histories, or secrets to the model is invisible until you look at the wire, and it is a privacy and cost problem at once.

Check 04

Can memory or context cross between users?

Run it

Store a unique fictional detail in account A’s history or memory, then talk to the assistant as account B and see whether it surfaces.

Why

Shared caches and memory stores are an easy place for one user’s data to leak into another user’s answers.

Check 05

Does revoking access actually revoke it?

Run it

Share something or connect an integration, then remove or disconnect it and retry the old request or link from the still-open session.

Why

Access should stop on the server the moment you revoke it, not just disappear from the screen.

Check 06

Do share links leak when you change the ID?

Run it

Open a share link in a private browser window with no login, then alter the identifier in the URL and see whether other items become reachable.

Why

A share link should expose only the one thing shared. Guessable or unscoped identifiers expose everything.

Check 07

Are file and image URLs protected on their own?

Run it

For any uploaded file or generated image, grab its direct URL and try it logged out and from another account.

Why

Apps often protect the page but leave the underlying file world-readable to anyone who has, or can guess, the link.

Check 08

What leaks through backups, exports, and temp files?

Run it

Run an export or backup, then check where the file lands and whether other apps on the device, or the wrong cloud account, can read it.

Why

Data that is safe inside the app often leaks through the side doors around it.

Check 09

Are third-party scopes minimal and reversible?

Run it

When connecting Google, Drive, or a calendar, note the permissions requested, then disconnect and confirm the old token can no longer read or write.

Why

Over-broad scopes and tokens that outlive a disconnection are common, and costly when the connected account holds real data.

Check 10

Does the server trust the client for identity or entitlements?

Run it

Replay a request with a changed user ID, owner ID, or an isPro / isAdmin-type field and see whether the server accepts it.

Why

The client can send anything. Identity, ownership, and paid-tier checks all have to happen on the server.
