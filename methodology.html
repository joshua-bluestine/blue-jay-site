Trust / Methodology

How a review is run, and how findings are rated

The same method on every app: agree the scope in writing, test by hand with real accounts, confirm every finding, rank it by what an attacker actually gets, then check your fix. Here is each step, what it maps to in OWASP, and the severity scale used in every report.

Rules of engagement

  • Written scope and authorization first. The app, environments, roles, testing window and exclusions are agreed in writing, and you authorize the testing, before anything starts.
  • Test accounts only. Testing uses accounts you create for the review. I don’t sign in as real users or change their data.
  • No disruption. No denial-of-service or load testing, no phishing or social engineering, and no attacks on the platforms you build on (Supabase, Firebase, Vercel, your AI provider) beyond your own project’s configuration.
  • Serious issues reported straight away. If I confirm something critical, such as a key that lets anyone read every user’s data, you hear about it the same day, privately, not in the final report.
  • Every finding confirmed by hand. Tools help me cover ground faster. Nothing goes in the report until I have reproduced it myself and can show the request and response that prove it. You won’t get a scanner dump.

How test accounts, evidence and reports are stored and deleted is on the privacy & data handling page.

The four steps

1. Map the app

Walk through every screen and role as a normal user while recording the traffic. List each data type, the API routes and database tables behind it, and who should be able to read or change it. This permission map is the plan for everything that follows.

2. Test the boundaries

Work through the map with two or more accounts: replay one user’s requests with another user’s session, call routes the interface hides, change IDs and fields, query the database directly with the public keys your app ships, and try to talk the AI feature into crossing the same lines.

3. Confirm and write up

Reproduce each issue, rate it on the scale below, and write it up in plain English with the evidence, the fix, and a prompt you can paste into Cursor, Lovable, Bolt or Replit. The report says what was tested and what wasn’t.

4. Recheck

After you ship fixes, I repeat the original checks and the obvious variations around them, then record the result for each finding: fixed, partly fixed or still open. AI tools sometimes fix one route and miss its siblings, so the recheck looks for that too.

What is tested, and the OWASP reference

Findings are mapped to the OWASP references a developer or customer’s security team will recognize: the OWASP Top 10, the API Security Top 10, the Top 10 for LLM Applications, and the requirements in the Application Security Verification Standard (ASVS).

The exact checks depend on your app and the written scope. A review is time-boxed: it finds what can be found by an experienced tester in the agreed time, and cannot prove an app has no vulnerabilities.

The severity scale

Each finding is rated by two questions: who can do it (anyone on the internet, any signed-up user, or only someone with special access) and what they get (everyone’s data, one user’s data, money, or very little). Severity sets the order you fix things in.

SeverityWhat it meansTypical example in an AI-built appWhen to fix
CriticalAnyone, often without an account, can read or change all users’ data, take over admin, or spend your moneyA Supabase service-role key or OpenAI secret key shipped to the browser; RLS turned off on the users tableNow, before anything else ships
HighAny signed-in user can reach another user’s data or perform actions they shouldn’tChanging an ID in a request returns someone else’s invoice; the chatbot answers with another customer’s recordsBefore more users sign up
MediumReal harm, but it needs unusual conditions or exposes limited dataNo rate limit on the AI endpoint, so a script can run up your bill; a member can see team settings meant for adminsWithin your next few releases
LowSmall leaks or missing hardening that make other attacks easierDetailed error messages revealing table names; sessions that never expireWhen convenient
InformationalNo direct risk; a note for laterA dependency close to end of support; a pattern that will become a problem as the app growsYour call
